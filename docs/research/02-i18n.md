# 02 – i18n batch upgrade research

Batch: `i18next` 25.10.10 → 26.7.x, `react-i18next` 15.7.4 → 17.1.x, `i18next-http-backend` 3.0.6 → 4.0.x
(+ `i18next-browser-languagedetector` 8.x, check only). Installed versions read from `node_modules/*/package.json`.

## Verdict: **GO** – upgrade all three together in one step, no intermediate hop, no code changes required.

## Peer-dependency constraints (from `npm view <pkg> peerDependencies engines`, i.e. the published package.json)

- `react-i18next@17.1.13`: `react >= 16.8.0`, **`i18next >= 26.2.0`**, `typescript ^5 || ^6 || ^7` (optional). → React 19 OK; TS 5.9 OK; **i18next must be ≥ 26.2.0**, so they must be bumped together (react-i18next 17 will not accept 25.x). 17.0.7 also relies on i18next ≥ 26.0.10 (`scopeNs`) (https://raw.githubusercontent.com/i18next/react-i18next/master/CHANGELOG.md, 17.0.7).
- `react-i18next@15.7.4` (current): `i18next >= 23.4.0`, `typescript ^5`.
- `i18next@26.7.0`: `typescript ^5 || ^6 || ^7` (optional) → TS 5.9 OK. i18next's CI checks types back to TS 5.0 (26.7.0 changelog, `ci:` line).
- `i18next-http-backend@4.0.x`: no peerDependencies; `engines.node >= 18` (repo is on node 20 → OK). Its 4.0.8/4.0.9 fixes use i18next ≥ 26.7.0/26.7.1 features but it degrades gracefully on older i18next (http-backend CHANGELOG 4.0.8, 4.0.9).
- `i18next-browser-languagedetector@8.3.0`: no peerDependencies (only `@babel/runtime`) → compatible with i18next 26. Its sync `detect()` is unaffected by the i18next 26.7 "async detector `callbackApi`" deprecation, which only concerns *async* detectors (26.7.0 changelog).

## Intermediate hop via react-i18next 16?  **No.**

- 16.0.0 = "major upgrade i18next dep to address #1865" (i.e. raises i18next peer); 16.1.0 adds `IcuTrans`. No API breaks listed. 17.0.0's only listed "potentially breaking" item concerns `transKeepBasicHtmlNodesFor` serialization (https://raw.githubusercontent.com/i18next/react-i18next/master/CHANGELOG.md, sections 16.0.0, 16.1.0, 17.0.0). Jumping 15→17 directly is supported; there is no migration guide requiring 16.
- Need i18next 26 anyway; i18next 25→26 is a single major.

## Breaking changes and repo impact

### i18next 26.0.0 (https://raw.githubusercontent.com/i18next/i18next/master/CHANGELOG.md, "## 26.0.0")
| Breaking change | Affects us? |
|---|---|
| Removed `initImmediate` (use `initAsync`) | No – `src/app/i18n/instance.ts:21-36` and `src/test/i18nForTests.js:6-13` don't use it |
| Removed legacy `interpolation.format` function | No – only `interpolation.escapeValue` is set (`instance.ts:28-30`) |
| Removed support notice / `showSupportNotice` | No – not used |
| Removed `simplifyPluralSuffix` | No – not used |

No other 26.0–26.7 entry is a breaking runtime change; 26.1–26.7 are fixes/features/types (reviewed all entries). 26.7.0 adds debug-only deprecation warnings for v27 (not v26 breaks). Relevant to us only informationally, `debug` is off: `fallbackLng` is set (`instance.ts:22`) so the "`dev` fallback" notice doesn't apply; language codes `es`/`en` are safe.

### react-i18next 16.x / 17.x
- 17.0.0 `transKeepBasicHtmlNodesFor` serialization – **not affected**: not used anywhere (`grep transKeep|shouldUnescape|defaultVariables|enableSelector src` → no hits). Our four `<Trans>` usages all pass an explicit `i18nKey` with positional children (`AboutPage.tsx:33,44`, `Notification.tsx:71`, `Introduction.tsx:24,30`), no `components` object, `values`, `count` or `tOptions`.
- Behavior fixes touching `Trans` in 17.0.x–17.1.x (components object key `0` 17.1.1, `count` in tOptions 17.1.6, `defaultVariables` merge order 17.0.21, `&nbsp;` with `shouldUnescape` 17.0.18) – **none used by this repo**.
- `useTranslation`/`useSuspense: false` is unchanged; we set `react: { useSuspense: false }` (`instance.ts:31-33`).

### i18next-http-backend 4.0.0 (https://raw.githubusercontent.com/i18next/i18next-http-backend/master/CHANGELOG.md, "### 4.0.0")
| Breaking change | Affects us? |
|---|---|
| Drops `cross-fetch`; **requires host-provided `fetch`** (alt: `alternateFetch`) | Not in browsers (modern browsers have fetch). Vitest runs on Node 20 (global `fetch`). Practically moot: see below |
| `engines.node >= 18` | OK (node 20) |
| Build moved to tsdown, single-file ESM/CJS, `exports` map unchanged | No |
| 3.0.4: only `{{lng}}`/`{{ns}}` interpolated in `loadPath` | Not affected – default `loadPath` is used (no `backend` option in `instance.ts`) |
| Security releases 4.0.2/4.0.3/4.0.4/4.0.10 reject unsafe chars in `lng`/`ns` | Not affected for default `/locales/{{lng}}/{{ns}}.json` |

**Why the backend is effectively inert for us (verified in installed source):** `instance.ts:23-26` passes inline `resources` and no `partialBundledLanguages`. i18next only loads from the backend when `!options.resources || options.partialBundledLanguages` (`node_modules/i18next/dist/esm/i18next.js:1900`, `:2113`). There is also no `public/locales` directory (`ls public`). So the backend never issues requests; the v4 `fetch` requirement cannot bite. (Note: the same rule holds in 26.x per the changelog not listing any change to this; re-confirm via tests after upgrade.)

**npm audit:** `npm audit --json` currently reports `i18next-http-backend` (direct, severity low) via GHSA-xvq9-wjp8-hwqf (range `<4.0.2`) and GHSA-3cmx-xjww-583x (range `<4.0.4`) – both CVSS 3.7. Later advisory GHSA-qh2f-jh77-hfwf is fixed in 4.0.10 (http-backend CHANGELOG 4.0.10, 4.0.2, 4.0.4). → install `^4.0.10` to clear all.

### i18next-browser-languagedetector
No upgrade required. Used as `.use(LanguageDetector)` with default options (`instance.ts:19`). 8.3.0 has no i18next peer constraint.

## Residual risks / unverified (to be checked by running the suite after install)
1. `instance.ts` is imported by `i18nForTests.js:3` (`ENGLISH`), so tests execute the full init with HttpApi + detector under jsdom → run `vitest` to confirm no fetch-related errors (expected none since the backend is skipped).
2. `tsconfig.json:22` uses `moduleResolution: "node"`; I did not verify i18next 26 / react-i18next 17 type resolution under it (our deep imports are only top-level `i18next`, `react-i18next`, `i18next-http-backend`) → run `tsc`/`npm run build`.
3. `returnNull: false` in `CustomTypeOptions` and init options (`instance.ts:14,35`) is a leftover from pre-v24 and already compiles on 25.10; I found no 26.x entry changing this, but `tsc` should confirm.
4. i18next 27 is announced ("follows in about a week", 26.7.0 changelog); not part of this batch. v27 changes (`fallbackLng` default `false`, `/` no longer escaped) don't hurt us: we set `fallbackLng` explicitly and `escapeValue: false`.
